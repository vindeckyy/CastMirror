Windows · Linux · Cast Streaming

Mirror your PC to a Chromecast or Google TV. No Chrome.

CastMirror finds Cast devices on your network, captures your whole screen or a single window with its sound, and streams H.264 and Opus over the same encrypted Cast RTP path Chrome uses. The Windows app is the main product; Linux has its own packages.

Capabilities

What it does

CastMirror speaks the Cast protocol directly: TLS on port 8009 for control and encrypted RTP over UDP for the picture and sound. It does not run a browser.

📺

One-Click Cast & Discovery

Finds Chromecasts, Google TV devices and Cast TVs over mDNS. If your router blocks mDNS, an opt-in subnet scan or Add by IP still works. A TV that goes off the network drops out of the list.

🖥️

Screen & Window Sharing

Share a whole display or one window. On Windows, window sharing uses Windows.Graphics.Capture, so a window in front of the shared one stays out of the picture. You can also share the sound of one app instead of the whole PC. On Linux: X11, and the Wayland portal picker.

📈

Live stats

Frame rate, bitrate, round-trip time and packet loss update while you cast, with a plain-language hint when the Wi-Fi is dropping packets.

🎬

Freeze and mute

Freeze the picture or mute the TV without ending the cast. Opt-in global shortcuts (Ctrl+Alt+C, F and M) work from any app on Windows; in-window shortcuts include Ctrl+Enter, F5, Ctrl+K, Ctrl+, and Ctrl+L.

🔄

Adaptive bitrate

An eight-step ladder lowers resolution, frame rate and bitrate when packets are lost and climbs back when the link recovers. After a dropped connection, a sleep or a Wi-Fi change it reconnects for as long as you allow (10–600 s).

🛠️

Diagnostics and privacy

Copy a bug report from the Logs window with the last part of every IP address masked. A crash saves a local minidump (newest 5 kept) and nothing is uploaded. There is no telemetry and no account; GitHub is contacted only if you click Check for updates.

Architecture

Native Capture to Cast UDP Pipeline

Cast keeps a playout buffer, so expect about 150 to 400 ms of delay depending on the preset (200 ms by default). Desktop pixels and system audio (WASAPI loopback on Windows, PulseAudio or PipeWire on Linux) are encoded, encrypted with a per-session AES-128-CTR key, and packetized into Cast RTP over UDP.

1. Install and build

Guide

Windows

Install the app from the Windows 1.0.4 release, or build it from source. Building requires MSYS2 (UCRT64) with GCC, CMake, Ninja, pkgconf, protobuf, OpenSSL, Opus, FFmpeg, nlohmann-json, gtest and libx264, plus the .NET 8 SDK for the WinUI 3 app (and Inno Setup 6 for the installer). Full steps are in docs/building.md.

# In an MSYS2 UCRT64 shell:
pacman -S --needed mingw-w64-ucrt-x86_64-{gcc,cmake,ninja,pkgconf,protobuf,openssl,opus,ffmpeg,nlohmann-json,gtest,libx264}

build-all.bat                            :: native core, CLI, tests + WinUI 3 app
ctest --test-dir build --output-on-failure
dotnet test tests\winui\CastMirror.Tests.csproj
package.ps1                              :: build, ctest, self-contained publish, licence & package checks
iscc installer\CastMirror.iss /DAppVersion=1.0.4
scripts\run_ubsan.ps1                    :: test suite under UBSan (needs mingw-w64-ucrt-x86_64-clang)
scripts\soak_windows.ps1 -Minutes 10     :: memory and handle soak

Windows requires Windows 10 version 2004 or later, 64-bit. Control traffic uses TCP 8009 and media uses UDP, so the installer adds Firewall rules for private and domain networks; for the portable zip, run scripts\setup_firewall.ps1 -Program <path to CastMirror.exe> from an elevated PowerShell.

  • CASTMIRROR_PACKAGE_DISTRO_SUFFIX (default empty): Insert a distro suffix into CPack package names (e.g. debian13).

Environment variables
  • CASTMIRROR_FORCE_SOFTWARE_ENCODE=1: Force FFmpeg software encoding (libx264 / fallback) even when VAAPI GPU acceleration is available.
  • CASTMIRROR_VAAPI_DEVICE=/dev/dri/renderD129: Use one specific VAAPI render node instead of probing /dev/dri/renderD*.
  • CASTMIRROR_FORCE_X11=1: Force X11 display capture instead of the PipeWire portal when running under a Wayland compositor via XWayland.
  • CASTMIRROR_CONFIG_DIR=/path/to/dir: Redirect config.json and logs away from the default per-user directory.
  • CASTMIRROR_LANG=de: Override the Windows WinUI UI language (en, de, es, fr).
  • CASTMIRROR_DISABLE_WGC=1: Disable Windows.Graphics.Capture on Windows.
  • CASTMIRROR_VERBOSE_JSON=1: Emit per-frame JSON diagnostic breadcrumbs to the log.
  • CASTMIRROR_CSS=/path/to/castmirror.css: Override the Linux GTK stylesheet.
  • CASTMIRROR_ALLOW_SYNTHETIC_CAPTURE=1: Allow generated test frames/audio when real capture is unavailable (tests only).
  • CASTMIRROR_MSYS2_BIN / CASTMIRROR_DOTNET_ROOT: Override MSYS2 UCRT64 and .NET 8 SDK paths in Windows build/packaging scripts.
Network and firewall (Linux)

Control traffic uses TCP 8009 (TLS) to the receiver. Media streams use UDP to the ephemeral port returned in the ANSWER. Both devices must be on the same local subnet. Helper script: scripts/setup_firewall.sh.

2. System Architecture & Design

Architecture

CastMirror is a C++20 engine (castcore) with a C API (ABI version 3) and three front ends: the WinUI 3 app (app/winui, .NET 8) on Windows, a GTK 4 + Libadwaita app (app/gui) on Linux, and the cross-platform CLI (app/cli). The Windows app calls the engine through P/Invoke and checks the ABI version at start-up.

Performance & Latency Contract

  • Connect to First Frame: ≤ 8 seconds typical (including TLS, app launch, and OFFER/ANSWER negotiation).
  • Glass-to-Glass Latency: ~200 ms typical on a clean 5 GHz LAN at the default targetDelay: 200. The value stays in a 150–400 ms band (Game starts at 150 ms, Cinema at 400 ms) and the adaptive controller steps it 150→200→300→400 ms under loss/jitter and back down when clean. Chrome's own default is 400 ms.
  • Teardown Budget: Clean Stop within ≤ 500 ms (guaranteed halt of capture, encoders, and UDP sockets).
  • Idle Safety: Capture and encoders never run in the background when disconnected.

Media Pipeline

  • Video path (Windows): DXGI Desktop Duplication for a display, or Windows.Graphics.Capture for a window → conversion to BGRA (HDR and 10-bit surfaces tone-mapped to SDR) → frame pacer (steady 30 or 60 fps) → GpuProcessor (letterbox scaling, BT.709 limited-range NV12/YUV420P) → Media Foundation H.264 (asynchronous hardware transforms supported, FFmpeg libx264 fallback) → FrameCrypto → RtpPacketizer → paced UDP.
  • Video path (Linux): X11 XRandR / PipeWire portal → BGRA or direct NV12 frame → GpuProcessor (letterbox scaling, BT.709 YUV420P/NV12 plane write) → Hardware VAAPI (h264_vaapi) / libx264 (or libopenh264) encoder (0 B-frames, zerolatency) → Annex-B NALUs → FrameCrypto (AES-128-CTR) → RtpPacketizer (Cast RTP) → Paced UDP socket.
  • Audio path (Windows): WASAPI loopback of the default speakers, or of one app through process loopback (Windows 10 2004+) → folded to 48 kHz stereo → Opus (64–256 kbps, 192 kbps default) → FrameCrypto → RtpPacketizer → UDP. Capture follows the default device when it changes.
  • Audio path (Linux): PulseAudio / PipeWire default sink monitor → PCM 48 kHz stereo (10 ms chunks) → Opus encoder (64–256 kbps, 192 kbps default) → FrameCrypto → RtpPacketizer → UDP. Host audio sink is muted by default during streaming and restored on Stop.

State Machine

All subsystems coordinate strictly through an explicit thread-safe state machine:

Idle → Discovering → Ready → Connecting → Negotiating → Streaming ↔ Reconnecting → Stopping → Idle
(Failed state transitions gracefully back to Idle or Reconnecting)

4. Cast Streaming Protocol Specification

Protocol

Google Cast screen mirroring uses a specialized real-time media protocol (not WebRTC ICE/DTLS and not HLS media playback).

1. Control Plane (Cast V2 TLS 1.2 :8009)

  • Connection: OpenSSL TLS 1.2 connection to device port 8009 (SSL_OP_NO_TLSv1_3).
  • Protobuf Frame: 4-byte big-endian length prefix followed by serialized CastMessage.
  • Namespaces:
    • urn:x-cast:com.google.cast.tp.connection — Virtual sender/receiver session bindings.
    • urn:x-cast:com.google.cast.tp.heartbeat — PING / PONG keepalive packets (2-second cadence, 6-second timeout).
    • urn:x-cast:com.google.cast.tp.deviceauth — Cast device certificate challenge / response verification.
    • urn:x-cast:com.google.cast.receiver — LAUNCH, STOP, and GET_STATUS requests.
    • urn:x-cast:com.google.cast.webrtc — JSON OFFER / ANSWER session negotiation.
  • Firmware Mirroring App ID: 0F5096E8 (audio + video display mirroring) or 85CDB22F (audio-only).

2. Media Plane (Cast RTP / RTCP over UDP)

  • RTP Profile: rtpProfile: "cast" with a 7-byte Cast header immediately after the 12-byte RTP header (plus an optional 4-byte adaptive playout delay extension on packet 0): 
    Byte 0:    Flags (Keyframe marker, Reference Frame ID present, extension count)
Byte 1:    Frame ID (lower 8 bits)
Bytes 2-3: Packet ID (16-bit packet index within frame)
Bytes 4-5: Max Packet ID (16-bit total packet count - 1)
Byte 6:    Reference Frame ID (lower 8 bits)
  • AES-128-CTR Crypto: Fresh random 16-byte key and 16-byte IV mask per session. Per-frame IV mixes frame_id with the IV mask.
  • Compound RTCP: Sender Reports (SR) paired with receiver CAST feedback packets containing:
    • Checkpoint Frame IDs acknowledging complete display rendering.
    • Loss bitmasks (NACK / CST2) detailing dropped UDP packets for immediate retransmit.
    • Picture Loss Indicators (PLI) signaling decoder desync and requesting an immediate IDR keyframe.

6. Physical Device Matrix

Hardware

No real-device soak runs have been recorded in the repository yet, so every row in the generated matrix reads _not measured_. Run scripts/soak_real_device.sh against physical hardware and regenerate with scripts/render_device_matrix.sh to populate: docs/DEVICE_MATRIX.md.

Playout delay bounds

  • Minimum target playout delay the sender will request: 150 ms.
  • Default target delay: 200 ms (Auto / High / Balanced / Smooth).
  • Maximum: 400 ms — the Cinema preset starts there and Game starts at 150 ms; the controller clamps every value to the 150–400 ms range.
  • The delay is adapted at runtime: AdaptiveController::StepUpPlayoutDelay walks 150→200→300→400 ms when jitter exceeds 30 ms or loss exceeds 3%, and StepDownPlayoutDelay walks back after 15 consecutive clean intervals.

Keyframe cadence & crypto

  • 2000 ms periodic intra-refresh, or an IDR on packet-loss bursts.
  • OpenSSL AES-128-CTR, hardware-accelerated via AES-NI / ARMv8 Crypto Extensions.
